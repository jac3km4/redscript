# Contributing

## Validation

Use stable Rust for builds, tests, and Clippy. Use the pinned nightly rustfmt to
honor the repository's formatting configuration:

```sh
cargo test --workspace --bins --lib --tests --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps --locked
rustup toolchain install nightly-2026-11-13 --profile minimal --component rustfmt
cargo +nightly-2026-11-13 fmt --all -- --check
```

Keep `--all-targets` in the Clippy commands: CI lints test code too, so plain
`cargo clippy` is not equivalent.

Check feature-bearing crates standalone. Combining crates in one command lets
downstream dependencies re-enable features on upstream crates, hiding missing
dependency features in standalone builds, so run each check separately:

```sh
cargo check --no-default-features -p redscript-community-ast --locked
cargo check --no-default-features -p redscript-community-parser --locked
cargo check --no-default-features -p redscript-io --locked
cargo check --no-default-features -p redscript-compiler-api --locked
cargo check -p scc-core --locked
```

CI also lints and tests the single-threaded default (`Rc`/`RefCell`) build
alongside the `sync` and `parallel` feature builds. To apply formatting rather
than check it, run `cargo +nightly-2026-11-13 fmt --all`.

Validate the release build:

```sh
cargo build --release --locked -p redscript-cli -p scc -p scc-lib
```

## Regression tests

- Frontend diagnostics: `crates/compiler/frontend/tests/data/`.
- Inferred types and call type arguments: frontend `tests/data/type-queries/`.
  Each free function must end with a value-returning statement; snapshots include
  its result type, direct call type arguments, and any compilation diagnostics.
- Generated bytecode: `crates/compiler/backend/tests/data/`.
- Formatter and code-edit behavior: each crate's `tests/data/`.
- Binary decoding and serialization: unit tests in `crates/io`.
- Output preservation on compilation failure: compiler API tests.
- C boundary behavior: C API tests.

Fixture tests use Insta snapshots. Review snapshot changes for correctness rather
than accepting them blindly. Bytecode snapshots do not verify game-runtime behavior.

## Correctness rules

- Every assembly error must prevent saving output, even without a source span.
- Lowering must preserve evaluation order and lazy evaluation. Keep generated
  initialization at the expression's execution point, including on loop back edges.
  The explicit legacy-compatibility exception is `UNSAFE_ARRAY_EVALUATION`:
  lowering reports a warning and continues the legacy array-prefix path in all
  modes. That path can still reorder or eagerly evaluate expressions and
  provides **no correctness guarantee**. Do not use compatibility acceptance as
  evidence that evaluation order is preserved or as a precedent for new fallbacks.
  Source-free `UNSUPPORTED_SKIP_ARGUMENT` remains a distinct hard error.
- Switches change the break target, but must preserve the enclosing loop's continue
  target.
- Treat malformed bundles as decoding errors: check indices, ranges, and address
  arithmetic rather than panicking. Decoding iterators must terminate after errors.
- Reject unrepresentable strings: prefixed lengths are limited to `u16` bytes, and
  NUL-delimited pooled strings cannot contain embedded NULs.
- Collection mutation guards synchronize serialization presence flags when dropped.
- Release builds abort on panic. C API ownership, borrowed lifetimes, and buffer
  contracts are documented in `crates/scc/capi/include/scc.h`; keep those contracts
  and the Rust API documentation consistent.

## Documentation

- Keep the language guides (`docs/`) consistent with compiler behavior, and prefer
  linking to a single canonical section over restating a rule in several files.
- `docs/types/*.md` filenames are embedded by `include_str!` in
  `crates/compiler/frontend/src/symbols.rs`; do not rename or remove them.
- Date-stamped probe logs and historical corpus counts belong in
  `docs/language-investigations.md`, not in the current-contract guides.

## Commits

Use lowercase Conventional Commit subjects, such as
`fix(io): reject oversized strings`. Keep independent fixes in separate commits.
